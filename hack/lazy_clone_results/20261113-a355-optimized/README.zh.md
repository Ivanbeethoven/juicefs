# A355：forkredis 读取优化前后

2026-11-13，现有 A355，同一份初始数据，同一套优化构建参数。旧版 `7aaafbe`，新版 `c8a4035`。每组新旧二进制交替执行，各 3 轮；同时重测原生 Redis JuiceFS。没有使用之前那轮耗时来代替本次旧版对照。

**单层 forkredis 耗时减少 24.5%–34.4%；Overlay 总耗时减少 39.3%–52.1%。额外一层的差距已接近单层，但新引擎相对原生 Redis JuiceFS 仍有成本。**

## 结果

下表为属性和目录项缓存 1 秒这一档。每个耗时取 3 轮中位数；比例按每对新旧结果计算后再取中位数。

| 负载 | 单层：优化前 → 后 | 单层耗时减少 | Overlay：优化前 → 后 | Overlay 耗时减少 |
|---|---:|---:|---:|---:|
| 两个小文件，13 B / 64 B | 1.605 → 1.211 s | 24.5% | 1.998 → 1.218 s | **39.3%** |
| 128 × 4 KiB | 1.439 → 0.944 s | 34.4% | 1.991 → 0.954 s | **52.1%** |
| 8 × 1 MiB，每次读 64 KiB | 2.062 → 1.528 s | 26.0% | 2.610 → 1.496 s | **42.7%** |

新版 Overlay 相对新版单层的配对开销中位数分别为 **+0.14%、+1.09%、−2.20%**。最后一组三轮为 −2.41% / −2.20% / +0.84%，按测量波动处理，不能宣称 Overlay 比单层更快。关闭三项 FUSE 元数据缓存时间后，三组额外开销中位数为 0.74%–1.03%，见 [完整结果](full-01/RESULTS.zh.md)。

原生 Redis 对照在两个构建间的配对耗时变化中位数为 0.1%、0.1%、1.7%（三组）。新版 Overlay 的耗时仍是原生 Redis 的 **1.60–1.88 倍**，未达到原生引擎水平。

## 改了什么

1. `gets` 和目录扫描以最多 128 个键为一批，将多个键、多个层的请求放进同一个 Redis pipeline，减少串行往返。
2. 默认增加 **16 MiB** 元数据读缓存。缓存逐层记录、缺失结果、删除标记和精确目录范围；目录为空也可命中。LRU 按键、值和条目开销限制容量。本次实测占用最大 **235,078 B，约 230 KiB**，没有继续扩大预算。
3. 写事务在成功提交的同一段 Lua 中释放自身读快照，省掉提交后的单独释放请求。写入内容和持久化格式不变。

URL 可配置缓存，例如 `&fork_cache_bytes=67108864` 为 64 MiB，`&fork_cache_bytes=0` 关闭。数据缓存仍为 128 MiB，预读和预取仍为 0；当前输入已经全热，增加数据预取不能解释这次收益。新增元数据缓存预算单独列出，没有把它当成原有数据缓存的一部分。

## 合批和缓存各有多少收益

额外完成 18 项对照：128 × 4 KiB、1 秒元数据缓存时间、3 轮，关闭新版的元数据读缓存。

| 配置 | 本轮旧版 Overlay | 新版 Overlay | 配对耗时减少 |
|---|---:|---:|---:|
| 只有合批，元数据读缓存关闭 | 1.979 s | 1.219 s | **38.4%** |
| 合批 + 默认 16 MiB 元数据读缓存 | 1.991 s | 0.954 s | **52.1%** |

两行是独立批次，各有自己的旧版对照。不能把两行百分比简单相加。缓存关闭时实测占用为 0，见 [消融结果](batch-only-01/RESULTS.zh.md)。

以 8 个文件的 Overlay 为例，列目录累计时间从 1,176.3 ms 降到 404.1 ms，打开文件从 1,005.6 ms 降到 670.1 ms，pread 从 284.0 ms 到 278.5 ms。主要收益来自元数据路径。计时期间 `ZREVRANGEBYSCORE` 从 13,832 次降到 0，`ZRANGEBYLEX` 从 512 次降到 0；缓存命中 14,340 次，未命中 0。小文件诊断用例仍有 1–2 次版本查询，没有称所有场景都为零。

Redis 总命令数没有归零：该组仍有 36,619 次（包含 Lua 内部命令），原生 Redis 为 3,330 次。每个事务固定版本、注册读快照和结束校验仍然执行；这是后续应继续拆分的路径，本次未单独测出各段占时。

## 一致性和验证

缓存属于单个客户端，隔离 Redis 数据库、卷和分支；每个条目绑定层版本及查询键/范围。版本由事务开始时的 Redis 原子操作固定，不以 TTL 代替版本判断。事务内修改优先于缓存；其他客户端提交后版本改变，新事务不使用旧上层条目。只有通过远端结束校验或提交校验的读取才进入共享缓存。过期读者、失败事务和已封存卷的旧写者不能靠缓存通过检查。

- 12 项 forkredis 顶层测试通过 `-race`，其中复用 8 组现有 POSIX 操作测试；新增覆盖跨客户端更新、空目录变为非空、删除标记、缓存返回值隔离、容量淘汰、分批扫描中的本地修改，以及失败/过期读取不能填充共享缓存。
- 原生 Redis / MemKV / 通用元数据的 37 项顶层测试通过，含子测试共 265 项；`go vet ./pkg/meta` 通过。
- A355 上真实 FUSE 检查通过：只读父层、两个子层隔离、写入、截断、空洞、删除、重命名、硬链接、符号链接、xattr、重挂载后的内容正确。fork 只增加分支头，仍未复制全部元数据。
- 108 项正式测量和 18 项消融全部通过预热、字节数及操作次数检查，计时期间对象 GET 和对象读取字节均为 0。另有 6 项预检，不混入正式统计。

没有运行包含 SQLite 的完整 `make test.meta.core`，也没有声称通过完整 CI；本次按用户要求只测 Redis 和内存 KV。日志在 [validation](validation)。构建使用 Go 1.27.1、`make juicefs.lite`，正常优化；构建时只有测试脚本未提交，因此 build-info 中 `vcs.modified=true`，已提交的 Go 代码对应 `c8a4035`。`build-command.txt` 是复现构建命令，最后一次构建检查的 `build.log` 显示目标已是最新。
