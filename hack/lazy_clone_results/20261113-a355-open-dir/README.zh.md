# A355：打开文件、目录合并优化及 1 万文件对照

本轮将小负载总耗时再降低 **2.7%–8.4%**。目录页及其属性合并做一次远端版本确认；热缓存读取不再创建无用的 Redis pipeline 和中间 map。写入、快照过期和封存校验没有放宽。

代码先推送，再在 A355 完成 90 项性能对照。每组 3 对，交换版本及对照顺序。1 万文件组使用 **10,000 个真实的 4 KiB 文件**，同一目录跨越分页；每次测量读取两遍，共 20,000 次 pread、81,920,000 B。另有本地和 A355 FUSE 正确性验证。

## 结果

耗时单位 ms，各列取三次中位数；降幅和相对原生倍数先逐对计算再取中位数，不能直接用表中两个中位数相除。原生列是新版二进制的普通 Redis 引擎，只读挂载；Overlay 始终可写。优化前为上一轮已经减少事务往返的版本。

| 文件输入 | 缓存 | 优化前 Overlay | 优化后 Overlay | 原生 JuiceFS | 配对耗时下降 | 新版/原生 |
|---|---:|---:|---:|---:|---:|---:|
| 13 B、64 B 两个文件 | 16 MiB | 717.3 | 671.9 | 644.5 | 8.4% | 1.019 |
| 128 × 4 KiB | 16 MiB | 611.7 | 595.1 | 564.6 | 2.7% | 1.054 |
| 8 × 1 MiB，每次读 64 KiB | 16 MiB | 981.0 | 949.4 | 936.9 | 4.2% | 0.971 |
| 10,000 × 4 KiB | 16 MiB | 10607.1 | 9775.2 | 9937.7 | 16.3% | 0.985 |
| 10,000 × 4 KiB | 64 MiB | 10993.9 | 10157.7 | 9988.2 | 3.8% | 1.071 |

小负载的 0.971 倍表示本轮接近原生，不能当作稳定超过原生。1 万文件的波动更大：16 MiB 下新版/原生为 0.804–1.044；64 MiB 下为 0.994–1.094。全部三对均保留，没有选最快一次。两档缓存按顺序分别测量，不能由两组中位数推断“大缓存导致变慢”。

## 哪些开销减少了

128 小文件组，打开并列目录从 **30.66 ms 降到 20.96 ms**；打开文件从 **346.92 ms 降到 340.67 ms**；pread 基本不变（145.72 → 145.26 ms）。本地缓存结果收集从 21.08 ms 降到 11.20 ms；远端版本确认从 189.89 ms 降到 186.49 ms。

两个小文件、128 小文件、8 大文件三组分别少了 **512、16、256 次 Redis API 执行**，恰好对应目录循环数。每个完整缓存目录页从两次版本确认变成一次。打开文件原来已只有一次版本确认，本轮保留它，减少的是本地分配与复制。

详见 [逐项总耗时、open/readdir/pread、事务分段表](COMPARISON.zh.md)；[comparison.json](comparison.json)保留全部配对比值。每组的 `txn-cells.csv` 包含开始事务、查询、结束事务、提交、缓存收集及版本确认耗时，以及 Redis 命令数。分段为客户端累计时间，包含等待，不能重复相加解释总耗时。Redis API 次数也不同于包含 Lua 内部调用的 commandstats。

## 1 万文件暴露的问题

16 MiB 组的缓存占用达到上限，但这不是重复查询的唯一原因。64 MiB 组只使用 **28.2–30.6 MiB**，仍有范围查询；六个 Overlay 单元在计时期间都记录到一次提交及一次 Redis HSET。16 MiB 组唯一没有这次提交的新版第 2 对只用了 8047 ms，也是该组最快的一次。

代码中 `baseMeta.refresh` 调用 `kvMeta.doRefreshSession`，后者更新会话过期时间；`forkCommit` 对任何这类提交都会推进分支 revision。上层记录与空结果按这个 revision 缓存，因此会话刷新也会使旧版本缓存无法直接命中。这是基于代码和提交计数的定位：本轮没有开启 Redis MONITOR，未直接记录该 HSET 的键，不能把每次更新都认定为心跳实测。

因此，1 万文件的降幅同时受到版本更新落在测量窗口中的位置影响，不能全部归因于本轮代码。64 MiB 没有证明稳定获益，**默认容量保持 16 MiB**。后续若拆分会话状态与文件元数据的失效范围，必须同时保留写者拒绝、事务冲突和旧客户端兼容；本轮没有实施或测量这项改动。

## 构建、一致性和测量条件

| 版本 | 源码提交 | 二进制 SHA-256 |
|---|---|---|
| 优化前 | `4f5a0ea25547e1becfbbb316dd9d6ca0537d6c00` | `28149916f1406395cff4a6b063def26936fea7d5f66720944627b17060a5aeb3` |
| 优化后 | `8aeb68f21be128d6fb62a1dc4aa6ca7cffef0f5b` | `39402a00dc462b0498ab90e0737f1c1674f895c8eed4776bc96ca61cd001abb9` |

脚本提交 `54a96ee` 只增加导入进度输出，发生在测量前。两个二进制均为正常优化的 Go release/lite 构建；新版命令见 [build.log](local/build.log)。新旧版本每组的元数据缓存预算相同。属性/目录项缓存 1 秒，open-cache=0，noatime，数据缓存 128 MiB，buffer 64 MiB，预读/预取为 0；O_DIRECT 确保每次读取经过 FUSE。

90 项均先完成至少两遍内容校验预热。所有计时区间对象 GET=0、对象读取字节=0，FUSE 次数与字节数逐项符合输入。这里使用本机 `file://` 对象后端和本机 Redis，**没有部署 RustFS**；对象指标不是 RustFS 服务端计数。性能输入没有上层文件修改，写入/截断/删除等由正确性测试覆盖。

- 15 项 forkredis 顶层 race 测试通过（含子项共 32 项）；另 4 项针对最终修改的 race 回归通过。可选 metadata-only scaling 未启用。
- Redis、MemKV 及通用元数据测试 37 个顶层测试通过（含子项 265 项，另 2 个不适用子项跳过）；`go vet ./pkg/meta` 和 gofmt 通过。没有运行 SQLite 或完整跨后端 CI。
- 本地与 A355 FUSE 验证通过：子层隔离、父层只读、写入、截断、删除、链接、扩展属性及重新挂载。新回归覆盖目录缓存缺项、分页游标被删、收集属性后发生并发写入，以及确认失败前不得发布旧属性。
- 全部测试挂载已卸载，专用 Redis 已停止；没有启动云机。回执见 [collection.json](collection.json)。

跨机 Redis、并发写入的性能、大于 1 万文件的规模及长期运行仍未验证。原生 Redis 引擎在同一源码树中未被本轮修改；这不是另一个上游版本的二进制对照。
