# A355：JuiceFS Overlay 热读开销

2026-11-13 在已有 A355 上完成。没有新建云机，没有 SQLite。二进制代码为 `7aaafbe3c40b1b377accffd00755a7259f4f44e9`，正常优化构建；本次只增加测试脚本，没有修改文件系统实现。

**当前版本增加一层 Overlay 后，两组较稳定的负载慢约 25%；128 个小文件那组中位数为 37.4%，但三轮波动很大。开销主要在目录和文件打开路径。**

## 结果

属性、目录项缓存均为 1 秒，三轮交替顺序。单层和 Overlay 使用相同 `forkredis` 引擎、同一个封存 lower；Overlay 是可写子层，文件内容尚未修改。

| 负载 | 本轮读取量 / 次数 | 单层中位耗时 | Overlay 中位耗时 | 配对开销中位数 | 三轮开销范围 |
|---|---|---:|---:|---:|---:|
| 两个小文件，13 B / 64 B | 39,424 B / 1,024 | 1.596 s | 1.999 s | +25.1% | 24.8%–26.3% |
| 128 个 4 KiB 文件 | 8 MiB / 2,048 | 1.440 s | 1.979 s | +37.4% | 4.5%–57.7% |
| 8 个 1 MiB 文件，每次读 64 KiB | 128 MiB / 2,048 | 2.056 s | 2.588 s | +25.6% | 24.6%–26.3% |

开销先按每对 `Overlay / 单层 - 1` 计算，再取中位数；不直接用表中两个中位耗时相除。全部 54 项测量通过：3 个负载 × 2 档缓存 × 3 轮 × 3 个对照。关闭三项元数据缓存后的结果也在 [完整表](RESULTS.zh.md)，没有混入上表。

这里的参数特意让每次读取进入 FUSE：使用 O_DIRECT，关闭 open-cache、预读、预取，JuiceFS 数据缓存固定 128 MiB。每次重新挂载并预热；计时期间对象 GET 和对象读取字节均为零，实际 FUSE 次数和字节数逐项等于输入。这个结果衡量热数据下的读取及元数据路径，不是完整默认配置的吞吐或真实 Agent 任务耗时。

## 慢在哪里

以 8 个文件那组为例，各操作累计时间的三轮中位数：

| 操作 | 单层 | Overlay | 差值 |
|---|---:|---:|---:|
| 打开、枚举、关闭目录 | 786.7 ms | 1,167.4 ms | +380.7 ms |
| 打开文件 | 841.9 ms | 991.7 ms | +149.8 ms |
| pread | 285.0 ms | 284.5 ms | −0.5 ms |

这些分别取中位数的差值用于定位，不要求相加后严格等于总耗时差。热数据读取本身没有显示出明显增加；主要时间消耗在拿到文件和目录信息之前。

同一组实测 Redis `ZREVRANGEBYSCORE` 从每轮 **6,916 次增加到 13,832 次**；目录索引 `ZRANGEBYLEX` 从 **256 次增加到 512 次**。源码 `pkg/meta/tkv_forkredis.go` 中，`get` 逐层查询，`gets` 逐项串行调用 `get`，`scan` 先逐层列键再逐项取值；目前没有复用空上层查询结果。这与查询计数翻倍和目录耗时增加相符。命令计数包含 Lua 内部命令，不等于网络往返次数；没有把每条命令单独计时，不能声称所有差值都来自某一条 Redis 命令。

128 个小文件那组的三轮 Overlay 耗时为 2.297 / 1.499 / 1.979 秒，单层为 1.456 / 1.435 / 1.440 秒。计时窗口跨越 1 秒缓存有效期，范围查询计数也有差异；尚未单独确认这能解释多少波动，所以保留全部三轮，不把 37.4% 当作稳定常数。

## 新引擎本身还有成本

同一二进制的原生 Redis JuiceFS 也测了，数据内容一致、独立卷、只读挂载。上述三组 Overlay 耗时分别是原生 Redis 的 **3.12 / 3.47 / 2.71 倍**（配对比值中位数）。因此不能把“增加一层约 25%”说成“相对原生 JuiceFS 只慢 25%”。

`forkredis` 单层已经包含逐键版本查询和每个事务的读快照注册、释放。新引擎的这些成本与层合并成本需要分别优化。本次没有实现或宣称优化收益，也没有与 BrewFS 作跨实验环境比较。
